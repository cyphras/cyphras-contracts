# Cyphras mainnet trusted-setup ceremony

This folder is the kit for the multi-party Phase-2 Groth16 ceremony that produces the
**mainnet** proving key for the `withdraw` circuit. No real funds may enter a pool before
this ceremony has run and its output is deployed.

## Why a ceremony

Groth16 needs a one-time setup that yields a proving key (zkey) and a verification key.
Generating it also produces secret randomness ("toxic waste"). Anyone who keeps that
secret can forge withdrawal proofs and drain every pool without depositing. The testnet
zkey is generated by one machine with reproducible entropy and is therefore forgeable by
design - fine for testnet, never for real funds.

A multi-party ceremony fixes this: several independent participants each add their own
secret randomness in sequence and each destroys their own piece. The setup is secure as
long as **at least one** participant is honest and discards their secret, so even if
everyone else colludes, one honest contributor makes forging impossible.

## What is public, what is secret

- **Public:** the circuit `withdraw.r1cs`, the Hermez powers of tau, every intermediate
  zkey, every contribution hash, the final zkey, and the verification key. The transcript
  publishes all of these. Intermediate zkeys can be moved over any channel; integrity is
  guaranteed by hashes and `verify`, not by secrecy.
- **Secret (must be destroyed):** each participant's contribution entropy. `contribute.mjs`
  generates it in memory only, never writes it to disk or the command line, and zeroes it
  before exit.

## Roles

- **Coordinator** (Cyphras): obtains and verifies the Hermez powers of tau, runs
  `groth16 setup` to create the first zkey, relays the file between contributors, verifies
  each returned contribution, applies the final public beacon, and publishes the transcript.
- **Contributors** (>= 2, ideally 3, at least one outside the Cyphras circle): each receives
  a zkey, runs `contribute.mjs`, sends the result back to the coordinator, and publishes a
  signed attestation. The coordinator is also one contributor, which guarantees at least one
  honest party.

Handoff is hub-and-spoke: the coordinator is the relay. Contributors never push to the
repository; they return their output to the coordinator and publish only their attestation
(name + contribution hash, signed). The coordinator publishes the public transcript here.

## Prerequisites

- Node.js 18 or newer.
- From this folder: `npm install` (installs the exact snarkjs version pinned for the ceremony).

## For a contributor

You receive from the coordinator: this kit, your input zkey, the expected sha256 of that
input, and (optionally) the circuit r1cs and the Hermez ptau for full verification.

```
npm install

# minimal: integrity-check the input by sha256, then contribute
EXPECTED_INPUT_SHA256=<hash the coordinator gave you> \
  node contribute.mjs withdraw_in.zkey withdraw_out.zkey "Your Name <handle>"

# recommended (outside contributor): also verify the full chain locally first
EXPECTED_INPUT_SHA256=<hash> R1CS=withdraw.r1cs PTAU=powersOfTau28_hez_final_14.ptau \
  node contribute.mjs withdraw_in.zkey withdraw_out.zkey "Your Name <handle>"
```

The script prints your **contribution hash** and the **output zkey sha256**. Then:

1. Send `withdraw_out.zkey` back to the coordinator.
2. Publish the printed attestation, signed (PGP, a signed git commit, or a Stellar-key
   signature), in the issue #9 thread so it can be matched in the transcript.
3. Delete your local copies once the coordinator confirms. The secret entropy is already
   gone (it lived in memory only).

## For the coordinator

`coordinator.mjs` tracks the relay so you never lose which file is which: it verifies every
returned zkey against the circuit and ptau before accepting it, names files canonically
(`withdraw_000N.zkey`), records the chain in `build/mainnet/ceremony-state.json`, and always prints
the next action. The state file is operational and gitignored; the public record is `TRANSCRIPT.md`.

```
node coordinator.mjs init                   # after `npm run mainnet:setup`, start tracking
node coordinator.mjs receive <file> "Name"  # verify a returned zkey, file it as the next step
node coordinator.mjs status                 # show the chain so far and the next action
node coordinator.mjs beacon <beaconHashHex> # apply the final beacon and verify
node coordinator.mjs transcript             # print the filled transcript table to paste into TRANSCRIPT.md
```

The numbered steps below are the underlying commands `coordinator.mjs` runs and verifies.

1. **Get the Hermez powers of tau (Phase 1).** Do not run a local Phase 1.

   The original `hermez.s3-eu-west-1.amazonaws.com` bucket is offline. Use a reputable mirror;
   trust comes from verification, not the source - `powersoftau verify` plus the pinned sha256
   (cross-checked against an independent published value) make any mirror acceptable.

   ```
   curl -L -o powersOfTau28_hez_final_14.ptau \
     https://storage.googleapis.com/zkevm/ptau/powersOfTau28_hez_final_14.ptau
   npx snarkjs powersoftau verify powersOfTau28_hez_final_14.ptau
   shasum -a 256 powersOfTau28_hez_final_14.ptau
   ```

   The verify must end with `Powers of Tau Ok!`. Record the sha256 in the transcript and cross-check
   it against an independent published value. Power 14 (2^14 = 16384) covers the circuit's 12,819
   constraints. This file is already prepared for phase 2, so do not run `powersoftau prepare phase2`
   on it.

2. **Create the first zkey.** From the `circuits/` directory (which has the build helpers):

   ```
   cp <verified ptau> build/mainnet/powersOfTau28_hez_final_14.ptau
   npm run mainnet:setup        # groth16 setup r1cs + ptau -> build/mainnet/withdraw_0000.zkey
   ```

3. **Relay.** Send `withdraw_0000.zkey` to contributor 1 with its sha256. Receive
   `withdraw_0001.zkey`, verify it, then send to contributor 2, and so on:

   ```
   node ceremony/mainnet/verify.mjs build/withdraw.r1cs \
     build/mainnet/powersOfTau28_hez_final_14.ptau build/mainnet/withdraw_000N.zkey
   ```

   `verify.mjs` prints every contribution hash; match each against the contributor's
   published attestation before continuing.

4. **Apply the final beacon.** Use a public, unpredictable value pre-announced in issue #9.
   Recommended: a drand quicknet round (announce the round number before it exists).

   ```
   # beaconHash = the 64-hex randomness of the announced drand round; numIterationsExp = 10
   # arg order is: <old.zkey> <new.zkey> <beaconHash> <numIterationsExp>
   npx snarkjs zkey beacon build/mainnet/withdraw_000N.zkey build/mainnet/withdraw_final.zkey \
     <beaconHash> 10
   npx snarkjs zkey verify build/withdraw.r1cs \
     build/mainnet/powersOfTau28_hez_final_14.ptau build/mainnet/withdraw_final.zkey
   ```

5. **Export the verification key and publish.**

   ```
   npm run mainnet:export-vk    # -> build/mainnet/verification_key.json
   npm run mainnet:parse-vk     # -> build/mainnet/vk_parsed.json (verifier contract format)
   ```

   Fill in `TRANSCRIPT.md` (r1cs hash, ptau source + hash, each zkey hash, each contribution
   hash + attestation, beacon source + value, final zkey/vkey hashes) and commit it here.
   `verification_key.json` and `vk_parsed.json` are committed; the zkey and ptau are not.

6. **Deploy mainnet.** Bundle `build/mainnet/withdraw_final.zkey` into the extension, deploy
   the mainnet verifier from `build/mainnet/vk_parsed.json`, then the factory and pools. The
   extension zkey and the on-chain verification key MUST come from this same ceremony output.

## Walkthrough (3 contributors)

A full run from each actor's point of view. The coordinator works in
`cyphras-contracts/circuits/`; each contributor works in the kit folder they received (the
contents of `circuits/ceremony/mainnet/`) with their input zkey, `withdraw.r1cs`, and the ptau
placed alongside `contribute.mjs`. The coordinator is also one of the contributors, which
guarantees at least one honest party.

### Coordinator: prepare

```
cd cyphras-contracts/circuits
mkdir -p build/mainnet
curl -L -o build/mainnet/powersOfTau28_hez_final_14.ptau \
  https://storage.googleapis.com/zkevm/ptau/powersOfTau28_hez_final_14.ptau
npx snarkjs powersoftau verify build/mainnet/powersOfTau28_hez_final_14.ptau   # "Powers of Tau Ok!"
shasum -a 256 build/mainnet/powersOfTau28_hez_final_14.ptau build/withdraw.r1cs   # record in TRANSCRIPT
npm run mainnet:setup                                  # -> build/mainnet/withdraw_0000.zkey
shasum -a 256 build/mainnet/withdraw_0000.zkey         # the hash you give contributor 1
```

Send contributor 1 the kit, `withdraw_0000.zkey`, that sha256, and (for full verify) the
`withdraw.r1cs` and the ptau.

### Contributor N

Each contributor takes `withdraw_<N-1>.zkey` and produces `withdraw_<N>.zkey`. Contributor 1:

```
cd cyphras-ceremony        # the kit folder, with withdraw_0000.zkey + r1cs + ptau inside
npm install
EXPECTED_INPUT_SHA256=<hash from coordinator> \
R1CS=withdraw.r1cs PTAU=powersOfTau28_hez_final_14.ptau \
  node contribute.mjs withdraw_0000.zkey withdraw_0001.zkey "Your Name <handle>"
```

Then send `withdraw_0001.zkey` back to the coordinator, publish the printed attestation
(signed) in issue #9, and delete your local copies. Contributor 2 does the same for
`0001 -> 0002`, contributor 3 for `0002 -> 0003`.

### Coordinator: between hops

After each return, verify before relaying to the next contributor:

```
node ceremony/mainnet/verify.mjs build/withdraw.r1cs \
  build/mainnet/powersOfTau28_hez_final_14.ptau build/mainnet/withdraw_000N.zkey   # "ZKey Ok!"
shasum -a 256 build/mainnet/withdraw_000N.zkey   # match the attestation; give this hash to the next
```

### Coordinator: finalize

```
# after the last contribution (here withdraw_0003.zkey), apply the public beacon
npx snarkjs zkey beacon build/mainnet/withdraw_0003.zkey build/mainnet/withdraw_final.zkey \
  <beaconHash> 10
npm run mainnet:zkey:verify     # "ZKey Ok!"
npm run mainnet:export-vk       # -> build/mainnet/verification_key.json
npm run mainnet:parse-vk        # -> build/mainnet/vk_parsed.json
shasum -a 256 build/mainnet/withdraw_final.zkey build/mainnet/verification_key.json \
  build/mainnet/vk_parsed.json  # record in TRANSCRIPT
```

For more than three contributors the pattern repeats: contributor N does
`withdraw_<N-1> -> withdraw_<N>`, the coordinator verifies between each hop, and the beacon is
applied once to the last contribution.

## Anyone can verify the result

```
npm install
node verify.mjs withdraw.r1cs powersOfTau28_hez_final_14.ptau withdraw_final.zkey
```

A "ZKey Ok!" result proves the final proving key derives from the published circuit and the
Hermez powers of tau through the published chain of contributions.
